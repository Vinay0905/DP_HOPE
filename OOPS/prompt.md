--------------------------------------------------
NON-NEGOTIABLE QUALITY BAR
--------------------------------------------------

This course must be 10/10 quality for an absolute beginner.

That means:
- every lesson must be extremely detailed
- every explanation must assume the student is a complete beginner to OOP
- every concept must be taught slowly before moving to harder ideas
- no rushed explanations
- no skipping intuition
- no assuming hidden prior knowledge
- no shallow definitions
- no vague summaries in place of real teaching

Write as if this course will be judged against the best beginner programming courses.

Every lesson should feel like:
- a proper chapter from a premium course
- a beginner-friendly textbook section
- a hands-on coding lesson
- an interview-prep resource

If a concept is easy to misunderstand, over-explain it clearly.

--------------------------------------------------
BEGINNER-FIRST TEACHING RULES
--------------------------------------------------

For every lesson:
1. Start from the most basic possible intuition.
2. Explain new words before using them heavily.
3. Never assume the student already understands object references, memory, instance behavior, inheritance chains, or interface-based design.
4. Break complex ideas into small steps.
5. Use multiple small examples before bigger examples.
6. Re-explain confusing points in a second simpler way if needed.
7. Explicitly mention what beginners usually misunderstand.
8. Include “what this does NOT mean” whenever a concept is commonly confused.
9. Distinguish syntax from concept. Do not teach only syntax.
10. Teach with patience and clarity, not just correctness.

--------------------------------------------------
MINIMUM LESSON SIZE
--------------------------------------------------

Each lesson must be long and substantial.

Minimum expected size:
- normal lessons: 1800 to 3000 words
- major lessons such as encapsulation, inheritance, polymorphism, abstraction, composition, SOLID, design patterns, and interview modeling: 2500 to 4000 words

Do not make lessons artificially short.
Do not compress major concepts.
Depth is mandatory.

--------------------------------------------------
EXPLANATION QUALITY RULES
--------------------------------------------------

For every important concept, explain all of the following:
- what it is
- why it exists
- what problem it solves
- what happens without it
- how Java expresses it
- how beginners misuse it
- how interviewers ask about it
- when to use it
- when not to use it

Whenever useful, include:
- intuitive explanation
- technical explanation
- code example
- pitfall example
- interview framing

--------------------------------------------------
CODE EXAMPLE QUALITY RULES
--------------------------------------------------

Every code example must be genuinely educational.

Do NOT give tiny useless examples unless they are the first step in a larger explanation.

Across the lesson, examples should progress like this:
1. smallest possible example
2. clearer realistic example
3. design-oriented example
4. bad example and corrected version

Every example must include:
- full code
- explanation before the code
- explanation after the code
- file placement
- run command
- expected output when useful
- why the code is written this way

For code explanations:
- explain the role of each class
- explain why each field exists
- explain why each method exists
- explain why access modifiers were chosen
- explain why the relationship between classes is appropriate

--------------------------------------------------
ABSOLUTE BEGINNER SAFETY RULES
--------------------------------------------------

Do not assume the student understands:
- heap vs stack intuition
- object references
- null
- constructor flow
- method dispatch
- overriding rules
- abstract contracts
- interface implementation
- equals vs ==
- why hashCode matters
- composition vs inheritance
- why mutable shared state is risky

When these appear, explain them patiently and explicitly.

--------------------------------------------------
LESSON WRITING RULES
--------------------------------------------------

Inside each .md file:
- use clean Markdown formatting
- use many headings and subheadings for readability
- keep paragraphs readable
- use bullet lists where helpful
- use tables when comparing similar concepts such as:
  - class vs object
  - overloading vs overriding
  - abstract class vs interface
  - inheritance vs composition
  - == vs equals
- use fenced Java code blocks
- make the lesson pleasant to read, not just dense

--------------------------------------------------
NO LOW-EFFORT OUTPUT
--------------------------------------------------

Do NOT do any of the following:
- short generic explanations
- repeating the same sentence in different words
- fake depth
- superficial examples
- placeholder text
- incomplete code
- unexplained jargon
- skipping beginner confusion points
- writing as if for someone already comfortable with OOP

If a lesson is not excellent, expand it until it is.

--------------------------------------------------
FINAL STANDARD
--------------------------------------------------

Before finishing each lesson, internally verify:
- Is this detailed enough for a complete beginner?
- Would this lesson still make sense to someone learning OOP for the first time?
- Are the examples strong enough to teach and not just demonstrate?
- Does this lesson help in interviews as well as coding?
- Is this good enough to be called a premium 10/10 course chapter?

If not, improve the lesson before moving on.
